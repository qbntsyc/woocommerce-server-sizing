## 为什么 WooCommerce 比普通 WordPress 吃资源

因为商店里最值钱的那部分流量，基本绕不过 PHP。

访客一旦加购，浏览器就带上 WooCommerce 的 session cookie，之后他看到的每个页面都由 PHP 现场生成，缓存帮不上忙。商品筛选和搜索走查询字符串，每一种组合都是独立 URL，几乎命中不了页面缓存，爬虫还特别喜欢把每个筛选组合都走一遍。

后台任务也吃资源。WooCommerce 用 Action Scheduler 发订单邮件、发 webhook、更新库存、处理订阅续费，默认跑在 WP-Cron 上，也就是靠访客请求触发。生意越好，后台任务越多，而触发它们的正是访客。

数据库会一路膨胀。订单、订单元数据、备注、日志都往里堆。从 WooCommerce 8.2 起新店默认启用 HPOS（高性能订单存储），订单存进专用表而不是 posts 表，查询更快；老店得自己去 **WooCommerce → Settings → Advanced → Features** 手动切换，不切就还在用旧结构。

结账环节还有外部依赖。支付和物流插件在结账时调用第三方 API，对方慢一秒，你的 PHP worker 就被占一秒。高峰期几个慢请求叠在一起，后面的客户就排队。

## 该买多大：三个问题算出内存和 CPU

不用背“2 核 4G 起步”这种口号，按自己店的情况算一遍更靠谱。

**第一问：高峰时同时有多少人在购物车或结账？** 每个这样的请求都会占住一个 PHP worker 直到页面构建完成。所需 worker 数 ≈ 每秒未缓存请求数 × 单页构建秒数，再加余量。

**第二问：每个 worker 吃多少内存？** 装了 WooCommerce 加几个插件，单 worker 通常几十 MB 到 100 MB 以上。PHP 总内存 ≈ worker 数 × 单 worker 内存。

**第三问：数据库有多大？** MariaDB 的 buffer pool 要装得下繁忙的订单表和商品表，这部分内存得单独留。

代入一组数字：高峰每秒 4 个未缓存请求，每页构建 0.5 秒，那么任意时刻约 2 个 worker 在忙，留到 6–8 个能应对尖峰。按 80 MB 一个算，PHP 侧约需 650 MB。再加上 MariaDB、Redis、系统和页面缓存，一台小店的独立服务器 2 GB 是合理起点。

投广告的店要往上加。广告带来的流量集中在几个小时内，且大量落在商品页和结账页，4 GB 内存加 2 vCPU 是常见的起算点，跑一段时间看真实数据再调。这些数字是起点，不是测量结果，最准的答案永远是自己店铺在促销期间的 CPU、内存和结账响应时间。

## 机器买回来必须做的六件事

买到配置只是上半场，下面这些不做，配置等于白买。

**1. 页面缓存必须排除购物车、结账、我的账户。** 还要排除带 WooCommerce session cookie 或购物车 cookie 的访客、已登录用户、所有 POST 请求、带查询字符串的 URL。这里有个容易被忽略的细节：`utm_*`、`fbclid`、`gclid` 这类广告追踪参数不算“查询字符串”，所以从广告点进来的访客照样能拿到缓存页，不必为了投放关掉缓存。

**2. 装 Redis 对象缓存。** 这是 WooCommerce 收益最明显的一项优化，专门削减那些绕不过 PHP 的请求里的重复数据库查询。购物车页、结账页、账户页省下的查询次数，直接换成更短的响应时间。

**3. 让服务器接管定时任务。** 在 `wp-config.php` 里设 `DISABLE_WP_CRON`，再用系统定时器每 5 分钟跑一次 `wp cron event run --due-now --quiet`。这样订单邮件和库存同步不再依赖有没有访客上门，也不会因为某个访客的超时限制而中断。

**4. 备份要能一键恢复。** 每小时、每 6 小时或每日三档，保留多份历史副本，出事能一键回滚。订单数据丢一次，损失比一年服务器钱多得多。

**5. `max_execution_time` 至少给到 120 秒。** 批量导入商品、生成报表这类操作很容易超时，默认的 30 秒不够用。同时确认 `memory_limit` 到 256 MB，不然高峰期购物车和结账页可能直接白屏。

**6. 支付网关的 webhook 地址要通。** 网关只接受 HTTPS 回调，防火墙如果把回调路径挡了，会出现“客户已付款但订单一直不完成”。上线前用网关的测试模式跑一笔完整订单，Stripe 和 PayPal 都提供测试卡。

安全这块还有两项。信用卡测试攻击、客户账户撞库、爬虫遍历筛选页是商店最常见的三类骚扰，WAF 加按 IP 限速能挡掉大部分。另外把 wp-admin 里的插件文件编辑器关掉，少一个入口。

## 什么时候共享主机其实就够了

不是所有店都需要 VPS。如果主机商能给到 PHP 8.3+、MariaDB 10.6+ 或 MySQL 8.0+、HTTPS、256 MB 内存上限，并且资源限制不苛刻，一天几十单的小店跑在共享主机上没问题。

判断标准是控制权。订单变多或者开始投广告之后，你需要自己调 PHP worker 数量、配页面缓存规则、把 cron 从访客请求里挪出来、加 Redis。共享主机通常不给你这些开关，VPS 给。雨云的云服务器支持一键部署宝塔、Docker、1Panel 这类面板，装环境不用从编译 PHP 开始。

## 几个常被问到的细节

**256 MB 到底指哪个值？** 两个都要看。一个是 PHP 的 `memory_limit`，一个是 WordPress 的 `WP_MEMORY_LIMIT`（在 `wp-config.php` 里写 `define( 'WP_MEMORY_LIMIT', '256M' );`）。服务器可以在 PHP 层设一个更低的上限，把那边的值压下去。改完在 WooCommerce → Status 页面复核实际生效的数字。资源吃紧的站点，512 MB 更稳。

**HPOS 要不要开？** 新店默认就是开的，不用管。2023 年之前建的老店需要在设置里手动切换。如果你的插件或自定义代码直接读 posts 表拿订单，切换前先确认兼容性，主题或插件可以用 `before_woocommerce_init` 钩子里的 `FeaturesUtil::declare_compatibility( 'custom_order_tables', __FILE__, true )` 声明支持。

**需要哪些 PHP 扩展？** cURL 或 fsockopen 是基础，WooCommerce 和 PayPal IPN 这类集成都要用；部分 WooCommerce.com 扩展需要 SOAP；做中文或其他非英文店铺，Multibyte String 必须有。伪静态还要服务器支持重写规则。装完在 System Status 页面能一次看全。

**1 核 1G 能跑吗？** 能装能开，但不适合当正经店铺。1 GB 内存要同时装 PHP-FPM、MariaDB 和系统，留给 WooCommerce 的余量很小，装两个插件就到顶。拿它做测试站或者练手可以，正式卖货建议直接从 2 GB 起。
